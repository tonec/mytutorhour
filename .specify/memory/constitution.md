# MyTutorHour Constitution

## Core Principles

### I. Tutor Approval Gates Every Parent Message (NON-NEGOTIABLE)

- Nothing generated by the system reaches a parent or guardian without explicit tutor approval.
- A parent update MUST move through `draft` → `approved` → `sent` | `copied`. Only content in
  `approved` state can be sent or copied; send/copy controls MUST be disabled otherwise.
- Any edit or regenerate after approval MUST return the update to `draft`.
- Every generated field MUST be editable by the tutor before approval.

Rationale: the tutor is accountable to the family; trust in the product depends on the tutor
always being in control of what is said.

### II. Private Notes Stay Private (NON-NEGOTIABLE)

- Tutor private notes (content marked "private:" / "note to self", stored in
  `tutor_private_notes`) MUST NEVER appear in parent updates, emails, copied text, analytics
  events, or logs.
- This MUST hold across regenerates, tone changes, and any future output type.
- Private notes MUST NOT be passed to the LLM when generating parent-facing text.

Rationale: tutors record candid observations about children; leaking them would be a serious
safeguarding and trust failure.

### III. Grounded, Validated AI Output

- The LLM MUST NOT invent facts. Anything not mentioned in the tutor's note MUST be left empty
  or `null` (e.g. no homework mentioned → `homework` is null and the update omits homework).
- LLM output MUST be validated against the versioned JSON contract (Zod schema). On failure:
  retry once, then show an error with the transcript/input preserved.
- Prompts MUST be versioned in the repo, and each generated output MUST record the prompt
  version that produced it.
- The transcript MUST remain visible to the tutor so they can see why an output is off.

Rationale: parents receive these words as the tutor's own; fabricated detail is worse than none.

### IV. Children's Data Privacy by Default

- Collect the minimum: student first name, subject, level (optional exam board/notes). No DOB,
  school, or surname by default.
- Every table MUST have row-level security scoped to `tutor_id = auth.uid()`. No query path may
  bypass per-tutor isolation.
- The Supabase service-role key and all provider secrets MUST be server-side only and never in
  the client bundle or repo.
- Audio is transient: it MUST be deleted after successful transcription (with an R2 lifecycle
  rule as backstop); only transcripts and outputs are kept.
- Student data MUST NOT appear in error logs or analytics events.
- Data stores MUST be in UK/EU regions; third-party processors MUST have a DPA and MUST NOT train
  on our data.
- Deleting a student or account MUST hard-delete all related rows and stored objects.

Rationale: we process children's data under UK GDPR; minimisation and isolation are the only
defensible defaults.

### V. Under Two Minutes, Mobile-First

- The core flow (lesson end → approved update) MUST be achievable in under 2 minutes median.
- Every core screen MUST be fully usable at 375px width with one-thumb primary controls, and
  core flows MUST meet WCAG 2.2 AA.
- Transcription and generation MUST run as async jobs with visible status
  (`uploading` → `transcribing` → `generating` → `ready`).
- A recording MUST never be lost to a network failure: keep it locally and offer retry.

Rationale: if logging a lesson takes longer than writing a text message, it will not become a
habit for a busy solo tutor on a phone.

### VI. Solo-First Simplicity

- Design for one self-employed tutor: no organisations, team roles, or setup wizards.
- Prefer narrow and excellent over broad: features listed as MVP non-goals (marketplace,
  scheduling, video, multi-tutor, student app, invoicing, AI progress analysis) MUST NOT be built
  without a constitution or spec amendment.
- Prefer boring, managed technology and the fewest moving parts; any added dependency or service
  MUST be justified in the feature plan.

Rationale: a solo builder with low fixed costs can only sustain a small, focused product.

## Technology & Security Constraints

- Stack: TypeScript (strict), Next.js App Router + React 19, Tailwind CSS v4, Supabase
  (Postgres + Auth), Cloudflare R2 for files, hosted on Cloudflare via vinext.
- Next.js APIs MUST be checked against `node_modules/next/dist/docs/` before use (this version
  differs from common training data).
- R2 buckets MUST be private with EU jurisdiction; access only via short-lived presigned URLs.
- Secrets live in Cloudflare/Supabase environment secrets; `.env*` files are never committed.
- Security headers (HTTPS, HSTS, CSP) MUST be set before any production launch.
- Cost target: under £0.05 per processed 60-second note (STT + LLM) at MVP; provider choices
  MUST be evaluated against this.

## Development Workflow & Quality Gates

- Features follow the Spec Kit flow: specify → (clarify) → plan → tasks → implement. Each plan
  MUST include a Constitution Check against Principles I–VI.
- Before merge: `npm run lint`, `npm run check-types` and `npm run test:unitRun` MUST pass.
  Formatting follows `.prettierrc` (enforced via ESLint).
- Unit tests use Vitest and React Testing Library, are colocated as `*.test.ts(x)`, and follow
  Arrange-Act-Assert. External network calls and the database MUST be mocked.
- Changes touching approval state, private notes, LLM output validation, RLS, or data deletion
  (Principles I–IV) MUST include automated tests covering that behaviour.
- Core user flows MUST have Playwright E2E tests in `e2e/` that run on desktop Chromium,
  Firefox and WebKit and on a 375px mobile viewport (Principle V). `npm run test:e2e` MUST pass
  before merging changes to those flows. E2E tests select by `data-testid`, then role, then
  text, and MUST NOT use fixed waits.
- Every new table MUST ship with its RLS policy in the same migration.

## Governance

- This constitution supersedes other practice documents. `CLAUDE.md`/`AGENTS.md` provide runtime
  development guidance and MUST NOT contradict it.
- Amendments are made via `/speckit-constitution`, recorded with a Sync Impact Report, and
  committed with a message stating the version change.
- Versioning: MAJOR for removing or redefining a principle; MINOR for a new principle/section or
  materially expanded guidance; PATCH for clarifications and wording.
- Compliance: every feature plan and code review MUST verify adherence; any deviation MUST be
  justified in the plan's Complexity Tracking section or the constitution amended first.
